# Workspace and sequential evidence

`WorkspaceLayout` keeps the navigator, editor and source in stable, keyed sibling sections. Moving, hiding and maximizing only change grid areas/visibility, so component state, pending edits and loaded PDF instances remain mounted. The initial layout puts the navigator at left (220 px), editor at center and source at right (400 px). Titlebars support drag docking or a keyboard position selector; occupied slots swap. Borders resize with the pointer or arrow keys. Layout preferences persist separately from drafts under `pydicate-studio:workspace:v1`; invalid preferences fall back to defaults. Narrow screens show one pane with controls to reach the others.

When a passage has no saved PDF location or local region draft, `next-service` derives earlier passage identities from the active project's source order. The last visited earlier passage has priority, then nearest earlier passages. The evidence service returns the first saved location bound to the currently selected, verified PDF fingerprint. The renderer also considers earlier unsaved region drafts in that same order. It clones page, rotation, zoom and regions with new region identities into a recoverable local working draft, explicitly labeled as inherited. Reading status does not change the evidence manifest; normal “Salvar regiões” confirms the current passage's evidence.

Existing saved locations and own local drafts take precedence, including explicitly cleared empty selections. Saved views carry their asset identity so replacing a PDF never transfers the previous witness's coordinates. A working draft records its saved baseline so unrelated passage saves can advance the manifest revision without inventing a same-passage conflict. A changed baseline retains the existing conflict protection.

Focused tests use actual PDF.js vector fixtures, temporary evidence services and simulated workspace editors. They verify inherited saved and unsaved geometry, restart recovery, deliberate clearing, witness isolation, stable mounted components, dock swaps, resizing and responsive access. No historical corpus writes or provider requests are involved.
