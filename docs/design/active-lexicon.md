# Active passage lexicon and interpretation notes

`passage_lexicon` reads the current raw expression and the selected source namespace. It follows lexical assignments, aliases, composite definitions, and helper arguments down to declared predicates. Each entry retains its variable name, definition, category, constructor elements, source path/line, and declaration fingerprint. Aliases remain separate named entries; repeated occurrences retain separate paths. Helper parameters bind to their actual arguments and are not invented as lexical entries.

This inventory describes source dependencies. Conditional/multi-statement helper bodies are marked as candidate dependencies with diagnostics. Local helper targets are not mistaken for similarly named global lexemes. Runtime grammatical roles remain the evaluated engine graph's responsibility. The source node associated with an expanded component selects its enclosing reference or helper argument; it does not imply that the component exists as a separately editable token in the passage.

`PassageLexicon` is the compact searchable inventory. General meaning/grammar notes belong to a lexical identity; occurrence notes additionally belong to source, passage, and the exact expression/expansion identity. The expression fingerprint participates in occurrence IDs: changing a structure preserves old interpretations in the notebook instead of attaching them to an unproven new occurrence. The project notebook searches all passages and exports notes plus revision history as JSON.

`electron/lexical-notes-service.cjs` stores per-project private JSON under the configured user-data directory, using hashed filenames, atomic replacement, serialized writes, optimistic note versions, and preserved prior revisions. Invalid stored data is reported and never overwritten. Notes do not modify the historical source or the engine's definition. The UI buffers pending text locally, autosaves after a short pause, and offers an explicit save; reloading the notebook refreshes optimistic versions after a conflict.

Validation: four isolated Python provenance tests, three Node persistence/conflict/corruption tests, and one browser selection/general-versus-occurrence/restart/export test. Read-only actual Araújo probes covered the full first passage (12 named entries, 14 uses), `credo(tuba)` (8 entries including nested `arobiar` components and bound `tuba`), and `ybyraîoasaba` expanded to `ybyrá` and `îoasaba`. These checks do not invoke a model or grant linguistic approval.

An independent production Electron run with separate temporary user data also exercised the actual first passage inventory, occurrence-note save and application restart, source-pane collapse/restore, and the ground-truth review panel without approval. It reported no renderer errors and verified the original Araújo source hash unchanged. The explicit “Localizar na estrutura” callback is separate from selecting a lexical entry, so browsing the inventory can retain context while an intentional reveal opens the editor.
